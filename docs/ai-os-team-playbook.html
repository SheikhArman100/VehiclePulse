§1Quickstart — copy the lines

The whole loop, minimal words. Sample project: acme-portal. Swap the name and follow along.

#### NEW PROJECT ########################################
desktop → "scaffold acme-portal as a web-app via dev-orchestrator"   # agent builds the tree — no script
ln -s CLAUDE.md AGENTS.md                  # one instruction file for every harness
desktop → "interview me, then fill knowledge/BRD.md and knowledge/SCHEMA.md"
# add Notion + Filesystem to your harness's MCP config ; paste the record protocol into AGENTS.md (§2 stage 3)

#### PER FEATURE — repeat until done ####################
desktop → "read playbook/features + PROGRESS.md, give me the coding-agent
           prompt for the next feature. don't write code, write the prompt."
cd acme-portal && opencode               # paste that prompt, let it build  (or: antigravity · claude)
  # run the project's test command — e.g. bun test / npm test

§2The run, explained

Sample: Acme Portal, a small internal status dashboard, greenfield. The spine underneath every step is Brain before Body — knowledge first, source last, because an agent that codes before the spec is real just produces confident nonsense faster.

One-time, per project

0

Set the context

■ Desktop app

Open the scoped Project for this surface; confirm its instruction doc is pinned. Drop in what you're starting from — an idea, a whitepaper, a PDF. The quality of the whole build is set here. Don't jump to the terminal yet.

1

Check the machine, then scaffold

■ Terminal

Confirm the environment, then lay down the structure. The dev-orchestrator skill does both — trigger it from the desktop project or the agent; it runs the pre-flight check and creates the tree directly, no script.

# ask the agent to run the dev-orchestrator pre-flight check
# (references/claude-code-setup-guide.md, Part 8): Node, Git, SSH, agent, configs
# then trigger the skill to scaffold — it reads references/project-archetypes.md
# and creates the acme-portal web-app tree directly. No script.
ln -s CLAUDE.md AGENTS.md          # scaffolder emits CLAUDE.md; this makes it portable

What lands — Brain→Soul→Body, plus the files the agent reads:

acme-portal/ ├── knowledge/ ← Brain (first): BRD.md, SCHEMA.md — still empty ├── design/ ← Soul (second): look & feel ├── specs/ ← chunked 8–15k tokens: architecture, data, API ├── playbook/ │ ├── features/ ← one file per feature, worked in order │ └── PROGRESS.md ← updated every session ├── src/ ← Body (last): the agent fills this ├── AGENTS.md ← the agent reads this first (→ CLAUDE.md on Claude Code) └── (MCP config) ← .mcp.json / opencode.json / ~/.gemini per harness
Decision point — risk gate

The scaffolder runs a risk assessment before writing specs. If it returns 🔴 High or ⛔ No-Go, stop and revise scope now — not after the agent has built a week of code on a bad premise.

2

Fill the Brain

■ Desktop app

The scaffolder interviews you — vision, platforms, stack, key flows, trade-offs. Its answers become knowledge/BRD.md (what it does) and knowledge/SCHEMA.md (how the data relates). Hold the line: no src/ until the Brain is real. An agent building against an empty spec is the most common way these go sideways.

3

Wire the record

■ Terminal + Notion

Give the harness its memory. Add Notion to your harness's MCP config, create this project's Project State row, and paste the protocol into AGENTS.md.

# MCP config — same server, config file differs per harness (the Team Guide §3):
#   Claude Code   .mcp.json          { "notion": { "type":"http", "url":"https://mcp.notion.com/mcp" } }
#   Antigravity   ~/.gemini/…        { "notion": { "serverUrl":"https://mcp.notion.com/mcp" } }   ← serverUrl
#   opencode      opencode.json      (mcp section — see opencode docs)
# also add the Filesystem MCP here — it's what lets desktop verify from source (step C).

# AGENTS.md — the record protocol, as rules the agent follows
START read Project State <row-id> + Canonical Facts <page-id>
END   rewrite Project State if it moved; log decisions to <db-id>
Filing reminder (the Team Guide §2)

The company, your project states, your decisions, and the canonical IDs go in Notion. The BRD, schema, and specs stay in the repo. Project State is a one-line row that says where this project stands — not the place for the spec.

Per feature — the build cycle

This is the loop you'll live in. A four-beat ping-pong between the desktop app (which plans and verifies) and your coding agent (which builds). You are the hand carrying prompts across.

REPEAT PER FEATURE
A

Desktop writes the prompt

■ Desktop app

Don't hand-write prompts for the coding agent. Ask the desktop project to write them — it has the specs and the record, so it writes better ones than you will.

You → Desktop"Read playbook/features/FEATURE_01_auth.md and PROGRESS.md. Write the exact prompt for the coding agent to implement Feature 01 — name the files to touch, the tests to add, and the acceptance check. Don't write code; write the prompt."

Copy what it gives back.

B

The coding agent builds

■ Terminal

Open the agent, paste the prompt, let it work. Then run the project's tests.

cd acme-portal && opencode     # or: antigravity · claude
# paste the prompt from step A, let it implement
bun test                       # the project's test command (npm test, etc.)
Context hygiene

Break at feature boundaries, not mid-feature. Keep PROGRESS.md current so a fresh session re-reads AGENTS.md + PROGRESS.md and knows where it is. Each harness has its own way to trim or restart a long session (Claude Code /compact, opencode session revert, Antigravity's manager) — use it before context gets heavy.

C

Desktop verifies, and writes the next prompt

■ Desktop app

Back to the desktop project. Because it can read the repo directly over the Filesystem MCP, you don't paste the diff — you point it at the folder.

You → Desktop"Read the changes in ~/Developer/acme-portal. Verify Feature 01 against FEATURE_01_auth.md: did it meet the spec, were tests added, was any test weakened to pass? If it's good, give me the prompt for the next feature. If not, give me the prompt to fix it."

It reads the actual files, gives you a verdict, and hands back the next prompt — which is step A again.

If your desktop project can't see the repo

No Filesystem MCP? Fall back to pasting the diff: run git diff in the terminal, copy the output, and give it to the desktop with the same verify request.

D

Human ships

■ Terminal

Only once the desktop says it's verified. Note the revert target first, then push. The agent never does this.

git rev-parse HEAD                    # write this hash down = revert target
git commit -am "feat: auth" && git push  # human ships
↺ next feature → back to A
What just happened

Desktop wrote the prompt → you carried it to the agent → the agent built → you carried the result back → desktop verified from source and wrote the next prompt → you shipped. The record updated itself over MCP at session end. That four-beat carry is the entire day-to-day. Everything else is setup you did once.

§3Variants & graduation

Existing repo, not greenfield

Skip stage 1's scaffold. Drop an AGENTS.md and your harness's MCP config into the repo, create the Project State row (stage 3), and start the cycle at step A. You inherit the code; you're wrapping the loop around it.

When you've done this enough

Once features are testable specs and you trust the loop, stop carrying prompts by hand. Declare the feature as a spec — goal, mandatory verifier, constraints, autonomy notch — and let the runtime decompose, dispatch, run, and verify it across whichever harness fits (it drives opencode, Claude Code, headless, and n8n alike). The verifier's verdict outranks the agent's self-report; autonomy is earned on clean runs. That's the graduation (the Team Guide §7). Don't reach for it before the four-beat carry is second nature.
